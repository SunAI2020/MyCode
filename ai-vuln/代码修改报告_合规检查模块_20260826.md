## 修改概述

本次实现了完整的**三标准合规检查子系统**，采用「自动技术检查 → 人工问卷填报 → AI 辅助研判」三阶判定模型：

| 标准 | 条款数 | 依据 |
|------|-------|------|
| 等保合规 | 65 条（10 个安全层面） | GB/T 22239-2019 网络安全等级保护基本要求 |
| 关基合规 | 46 条（6 个域） | GB/T 39204-2022 关键信息基础设施安全保护要求 |
| 数据安全合规 | 48 条（9 个域） | 《数据安全法》《个人信息保护法》/ DSMM GB-T 37988-2019 |

新增代码 **6120 行**，其中条款目录 JSON 2411 行、核心代码 2390 行、测试 1319 行。

## 详细修改

### 阶段 0：资产合规字段（`database.py`）

`assets` 表新增三列并做 `ALTER TABLE` 兼容迁移：

- `dengbao_level` — 等保定级，决定该资产适用的条款集（L2/L3）
- `business_system` — 业务系统，是问卷答案的**作用域键**
- `data_classification` — 数据分类分级

同步加入 `add_asset` 的 INSERT 与 `update_asset` 的 `ALLOWED_COLUMNS`（后者若遗漏会导致更新被静默丢弃）。

### 阶段 1：条款目录与判定引擎

**`compliance_controls/{dengbao,cii,data_security}.json`** — 条款目录外置为 JSON，扩充纯问卷条款无需改代码。每条含 `mode`（auto / questionnaire / hybrid）、`check`（自动评估器名）、`evidence_type`、`scope`（org / system）、`weight`、`question`、`evidence_hint` 等字段。

**`compliance_engine.py`（529 行）** — 引擎核心：

- **六态判定**：符合 / 部分符合 / 不符合 / 不适用 / 未填报 / 证据不足
- **计分规则**：分母**仅含**符合、部分符合、不符合三类；不适用 / 未填报 / **证据不足一律排除**
- **AI 降级表**（`score_factor`）：

  | 状态 | AI 研判 | 系数 |
  |------|---------|------|
  | 符合 | 认可 / 未运行 / 未完成 | 1.0 |
  | 符合 | 存疑 | 0.5 |
  | 符合 | 矛盾 | 0.0（状态已被强制改判为不符合） |
  | 部分符合 | 任意 | 0.5 |
  | 不符合 | 任意 | 0.0 |
  | 不适用 / 未填报 / 证据不足 | 任意 | 不计分（None） |

- **hybrid 合并取较差者**：技术检查判「符合」但人工填报「不符合」→ 取不符合
- **`apply_ai_verdicts` 矛盾强制改判**：AI 发现自评与技术事实冲突时，状态强制改为不符合——自评不得凌驾于扫描到的硬事实之上
- **`build_evidence()`**：把扫描结果行归一化为 `EvidenceBundle`；`scan_rows=None`（无证据）与 `[]`（扫过但无发现）语义严格区分

**`compliance_checks.py`（530 行）** — 12 个自动评估器：传输加密、身份鉴别、入侵防范、漏洞修补、KEV 处置、恶意代码防范、边界访问控制、数据库暴露、数据分类分级、工控协议暴露、国产化适配、Web 安全响应头。

> **关键设计原则：没有证据 ≠ 合规。** 评估器缺证据或崩溃时一律返回「证据不足」，绝不默认判「符合」。

### 阶段 2：合规结果数据库（`database.py`）

新增**第 6 个数据库** `compliance_results.db`，三张表：

| 表 | 用途 |
|----|------|
| `compliance_history` | 每次检查一条历史（合规率、得分、六态计数、自动占比、问卷完成度、AI 开关） |
| `compliance_control_results` | 条款级明细（状态、来源、AI 研判、权重、依据、整改建议） |
| `questionnaire_answers` | 问卷答案，`UNIQUE(standard, scope_key, control_id)` + UPSERT |

`Database` 门面注册 `self.compliance` 并转发 5 个便捷方法；`clear_database` / `close` 同步加一行；今日工作矩阵 `work_types` 由 7 类扩至 **10 类**（新增等保合规 / 关基合规 / 数据安全合规）。

**组织级答案跨系统复用**：`scope='org'` 的条款（制度、机构、人员）落在 `ORG` 作用域，所有业务系统共享；`scope='system'` 的条款按业务系统隔离，系统级答案覆盖组织级同名答案。

### 阶段 3：问卷引擎与 AI 研判层

**`compliance_questionnaire.py`（210 行）** — 抽取待填条款、读写答案、统计完成度。`normalize_status()` 认不出的状态返回 `None` 并**拒绝写库**，不猜成「符合」。

**`compliance_ai.py`（419 行）** — 四种能力：`suggest_answers` / `review_answers` / `cross_check` / `generate_remediation`，批量 4 条 × 并行 3 批。

> ⚠️ **失败方向与 `ai_scan_enhancer` 相反，这是本次最需要注意的一点：**
> `ai_scan_enhancer` 调用失败时**保留漏洞**（保守 = 不漏报）；
> 本模块调用失败时返回 `ai_status='未完成'`，**绝不返回「认可」**。
> 原因：合规研判里「认可」是一项声明——声称 AI 已核验过这条自评。调用失败却回填「认可」，等于凭空捏造一次并不存在的核验，会让报告里的「AI 已核验 N 条」变成谎报。
> 该规则由 7 项单测逐条锁定（异常 / 空响应 / 无法解析 / 模型漏答 / 模型胡诌状态 / AI 不可用）。

### 阶段 4：合规报告（`compliance_report.py`，318 行）

单 f-string + 内联 CSS，镜像 `report_generator._generate_audit_html`。含汇总卡片网格、按安全层面统计表、条款判定明细表（状态 / 来源 / AI 研判三色着色，问题项优先排序）。

**页脚强制披露**（不可删除，由 6 项测试锁定）：

- 自动技术检查判定占比、问卷填报完成度
- 合规率分母口径说明（哪些状态不计分）
- AI 矛盾 / 存疑 / **未完成**项数——「未完成」明确标注为**未经过 AI 核验**
- 「证据不足」显式警告**请勿理解为符合**
- **本报告不构成等级保护测评、认证或第三方审计结论**

### 阶段 5：GUI（`main_window.py` + `compliance_dialog.py`）

- **两个工作线程**：`ComplianceCheckThread`（证据装配 → 判定 → AI 研判 → 落库）、`ComplianceAISuggestThread`
- **三个标签页**：等保合规 / 关基合规 / 数据安全合规，**追加在最后（索引 11/12/13）**——`_on_tab_changed` 按硬编码索引 0~10 分发，前插会导致全部错位
- **防陈旧线程**：信号回调用 lambda 捕获线程对象，`self._compliance[k]['thread'] is t` 校验后才回写界面
- **`_populate_compliance_table`**：AI 判「矛盾」整行标红、「存疑」标橙、「不符合」浅红底
- **`compliance_dialog.py`（263 行）**：问卷填报对话框独立成文件。AI 建议经 `ai_suggest_requested` 信号交给主窗口线程执行，对话框本身不发起耗时调用。**AI 建议只填「AI建议」列，不直接改判定——AI 不替填报人签字**
- **工作埋点**：`start_work` / `finish_work` 覆盖进行中 / 已完成 / 被终止三态，接入仪表盘今日工作图表

## 端到端验证结果

在临时数据库上完整走通「设资产字段 → 扫描 → 填问卷 → 合规检查 → 出报告」：

```
== 1. 资产三字段 ==
  写入: L3 OA系统 重要数据
  更新: L2 财务系统 核心数据
  表格列数: 16  末三列表头: ['等保定级', '业务系统', '数据分类']

== 2. 扫描证据 ==
  扫描任务 #1，2 条结果（23/telnet 明文 + 3306/mysql CRITICAL 未授权）

== 3. 问卷填报 ==
  DB-CN-02 自评「符合」，说明「已全程启用TLS加密，无明文协议」
  填报进度: 2 / 65

== 4. 合规检查 ==
  合规率=0.4407  得分=44
  符合=4  部分符合=7  不符合=5  证据不足=0  未填报=49
  自动判定占比=0.2308
  DB-CN-02 判定 = 不符合 | 来源 = auto
  依据 = [技术检查] 检测到 1 个明文传输服务：Telnet/23@10.0.0.1，账号口令与业务数据
         以明文在网络中传输 | [人工填报] 已全程启用TLS加密，无明文协议
```

**hybrid 取较差者生效**：自评「符合」被技术检查的明文 Telnet 端口压倒，判为不符合，且两侧依据都保留在报告里。

**专项验证 — AI 矛盾检测强制改判：**

```
== 5. AI 矛盾强制改判 ==
  输入: DB-CN-02 自评「符合」，权重 2.0
  AI 研判: 矛盾（扫到 23/telnet 明文端口）
  改判后 = 不符合   严重度 = CRITICAL   计分 = 0.0
  依据含改判说明: True
```

**结论：矛盾项被强制改判为「不符合」，权重 2.0 触发 CRITICAL 严重度，合规率计分归零。**

## 设计要点回顾

1. **没有证据 ≠ 合规** — 缺证据判「证据不足」并排除出分母，绝不默认「符合」
2. **技术事实压过自评** — hybrid 取较差者；AI 判矛盾时强制改判不符合
3. **AI 失败判「未完成」而非「认可」** — 不捏造并不存在的核验（与 `ai_scan_enhancer` 方向相反，已加注释 + 单测锁定）
4. **不冒充测评结论** — 报告页脚强制披露自动占比、问卷完成度、未核验项数，并声明不构成等级测评/认证结论
5. **组织级答案复用** — 制度类条款填一次全局共用，不逼用户逐系统重复填报
6. **截断显式告知** — AI 整改建议按权重取 Top-N 时，回调告知剩余未生成条数，不伪装成全量覆盖
