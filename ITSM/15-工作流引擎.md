# 步骤十五：可配置工作流引擎（阶段五 · FR-18）

> 依据：《IT运维集中管控平台_软件设计方案.html》V1.0 定稿 · §4.17 / §6.2
> 范围：状态流转规则可配置（DB 覆盖/扩展内置默认）+ 全量动作留痕；替换工单/变更/外包三处硬编码状态机。

## 1. 目标

将散落在 `work_orders.py`（工单）、`change_service.py`（变更）、`outsourcing_service.py`（外包）的硬编码 `TRANSITIONS` 状态机收敛到统一「可配置工作流引擎」：默认流转内置兜底（开箱即用、既有测试不受影响），管理员可在 DB 新增/禁用流转规则覆盖或扩展默认；每次流转写入 `action_log` 全量留痕（触发规则、时间、操作人），呼应 §4.17「全量留痕」。

## 2. 表（2 张，依据 §6.2 `workflow_rule` / `action_log`）

- `workflow_rule` 工作流规则：`id, entity, from_status, to_status, name, auto_action, enabled, created_at`
- `action_log` 动作日志：`id, entity, entity_id, rule_id, from_status, to_status, operator_id, note, created_at`

## 3. 业务规则

- **实体** `entity`：`work_order` / `change_order` / `outsourcing`（其余实体后置）。
- **默认流转** `DEFAULT_TRANSITIONS`：内置三套状态机（与现状逐字节一致），作为兜底。
- **DB 覆盖/扩展**：`workflow_rule`（`enabled=true`）允许的 `from→to` 与默认取并集——既新增迁移，也支持禁用默认（禁用规则不可扩展为「禁止」，仅管理自定义边）。
- **非法流转**：`from→to` 不在并集中抛 `ValueError("非法状态流转：X → Y")`（API 层转 400）。
- **全量留痕**：每次成功流转写 `action_log`，记录实体、主键、前后态、操作人、备注。
- **同态幂等**：`target == from_status` 视为合法（不写日志）。

## 4. 文件清单

- `app/models/workflow.py` — `WorkflowRule` / `ActionLog`
- `alembic/versions/0009_workflow.py` — 迁移
- `app/schemas/workflow.py` — 请求/响应模型
- `app/services/workflow_service.py` — 引擎：`allowed_targets` / `assert_transition` / `log_transition`
- `app/api/v1/workflows.py` — 规则 CRUD + 有效流转查询
- `app/api/v1/work_orders.py` / `change_service.py` / `outsourcing_service.py` — 接入引擎
- `tests/test_workflow_service.py` — 单测

## 5. API

- `GET /workflow-rules?entity=` 规则列表
- `POST /workflow-rules` 新增规则（`sys_admin`）
- `PUT /workflow-rules/{id}` 修改/启停（`sys_admin`）
- `DELETE /workflow-rules/{id}` 删除（`sys_admin`）
- `GET /workflow-rules/transitions` 各实体有效流转（默认 ∪ DB），供前端配置界面

## 6. 角色

规则管理属平台域：读写 `sys_admin`；读 `sys_admin / sys_ops / ticket_mgr`。流转本身由各业务端点既有角色控制，引擎仅做合法性校验与留痕。
