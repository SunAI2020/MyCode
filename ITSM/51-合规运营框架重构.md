# 51-合规运营框架重构（安全服务 3.0 理念落地）

> 借鉴对象：小西牛「安全服务 3.0（合规运营）」产品理念
> 融入方式：重构现有模块 —— 把问题整改、报告中心、履约洞察等散点留痕收编进统一合规框架
> 性质：**设计文档（本文档先行，评审通过后再编码）**

---

## 一、背景与目标

### 1.1 理念内核

小西牛「安全服务 3.0」的核心主张，可提炼为四句话：

| 主张 | 含义 |
|---|---|
| **合规为底** | 合规不是配套服务，而是政企安全建设的底层刚性要求（公安部 176 号令落地，清单式核查 → 结果导向、闭环追责、履职溯源） |
| **履职免责** | 视角从「乙方工具交付」翻转为「甲方尽职履责」，所有动作围绕客户「履职免责、风险可控、全程可溯」展开 |
| **全程留痕** | 技术、组织、制度、台账、全流程管控五大维度全程可追踪、随时可核验、成果可沉淀 |
| **量化可控** | 合规梳理预判 → 落地整改执行 → 实战攻防校验 → 全程溯源留痕，形成可量化运营的闭环 |

### 1.2 ITSM 的现状与缺口

ITSM 是一条「合同 → 项目 → 服务对象 → 服务项目 → 工单」的履约管控平台，底层已经具备六类留痕能力，但**彼此割裂、缺少统一到「合规」视角的框架层**：

| 现有模块 | 现状能力 | 相对合规视角的缺口 |
|---|---|---|
| 问题整改闭环 `issue/rectification` | 问题→多轮整改→效果验证 | 问题未绑定「合规条款」，闭环≠合规闭环 |
| 变更单 `change_order` | 风险评估+冲突+回滚+审批 | 变更留痕未进证据链 |
| 审批流 `approval` | 通用状态流转审批 | 审批留痕未进证据链 |
| 交付 `delivery` | 报告 + 签署 | 签署即关键「履职自证」，但未被显性使用 |
| 审计日志 `sys_audit_log` | 写操作留痕 | 操作留痕与业务证据未打通 |
| 报告中心/看板 `dashboard` | 客户/合同/工单/交付等统计 | 缺合规覆盖率、闭环率、留痕完整率、风险敞口 |
| 合同履约洞察 `contract_insight` | 临近到期 + 履约缺口 | 缺「合规覆盖缺口」预判 |

### 1.3 目标

在既有履约主轴上**叠加一层合规运营框架**（合规台账），把上述散点留痕统一映射为
`合规要求 → 履约证据 → 履职报告` 的可溯源闭环，落地「履职免责、全程留痕、闭环追责、量化可控」，
同时**不破坏现有主链路与既有模块**（叠加 + 收编，非推翻）。

## 二、理念对照（安全服务 3.0 → ITSM 落地）

| 小西牛 3.0 概念 | ITSM 落地实体 | 说明 |
|---|---|---|
| 合规为底 | 合规要求库 `compliance_requirement` | 监管要求 + 合同义务条目化，作为全局底座 |
| 五大维度（技术/组织/制度/台账/流程） | 合规要求 `category` 分类 | 一条要求必属一类，支撑分维覆盖分析 |
| 全程留痕/可溯源 | 合规证据 `compliance_evidence` | 自动采集 + 人工上传，带内容哈希防篡改 |
| 闭环追责 | 合规核验 `compliance_check` | 核验状态机，不通过自动接问题整改闭环 |
| 履职免责/自证 | 履职报告 `duty_report` | 从证据链自动聚合，可导出/签署 |
| 量化可控 | 合规指标（覆盖率/闭环率/留痕完整率/风险敞口） | 接入看板与履约洞察 |
| 合规梳理预判 | 履约洞察升级 | 新增「合规覆盖缺口」预判 |
| 实战攻防校验 | 整改效果验证（复测）挂接核验 | 效果=通过 即 核验=通过 |

## 三、现状盘点：被收编的现有模块

| 现有模块 | 表 | 在合规框架中的新角色 |
|---|---|---|
| 问题整改闭环 | `issue` / `rectification` / `rectification_record` | **闭环追责执行层**：问题=合规缺口，整改轮次=整改动作，效果验证=核验通过 |
| 变更单 | `change_order` | 变更留痕证据源 |
| 审批流 | `approval` | 流程管控留痕证据源 |
| 交付 | `delivery` | 交付留痕 / 履职自证证据源（签署=强证据） |
| 审计日志 | `sys_audit_log` | 操作留痕证据底座 |
| 报告中心/看板 | `dashboard.py` | 升级为「合规运营看板」 |
| 合同履约洞察 | `ai_service.contract_insight` | 升级为「合规预判」（覆盖缺口） |

> 收编原则：**现有表零破坏**。证据通过 `compliance_evidence.source_type/source_id` 关联现有实体，
> 不复制数据；唯一对现有表的结构性改动是给 `issue` 增加一个可空外键 `requirement_id`（见 §五）。

## 四、核心设计：合规台账框架（Compliance Ledger）

```
                     ┌─────────────────────────────────────────────┐
                     │            合规要求（ComplianceRequirement）      │  合规为底
                     │  来源：监管要求模板 / 合同义务提取 / 人工录入      │
                     │  分类：技术·组织·制度·台账·流程（五大维度）       │
                     └──────────────────┬──────────────────────────┘
                                        │ 1:N（一条要求 → 多条证据）
                     ┌──────────────────▼──────────────────────────┐
                     │            履约证据（ComplianceEvidence）         │  全程留痕
                     │  自动采集：工单完成/整改通过/变更完成/交付签署/审批  │
                     │  人工上传：报告、签字件、截图（带 SHA-256 哈希）   │
                     └──────────────────┬──────────────────────────┘
                                        │ 证据支撑核验
                     ┌──────────────────▼──────────────────────────┐
                     │            合规核验（ComplianceCheck）            │  闭环追责
                     │  未覆盖→进行中→已核验 / 有缺口→整改→已闭环        │
                     └──────────────────┬──────────────────────────┘
                                        │ 聚合输出
                     ┌──────────────────▼──────────────────────────┐
                     │            履职报告（DutyReport）                │  履职免责
                     │  覆盖矩阵 + 证据清单 + 闭环情况 + 量化指标         │
                     └─────────────────────────────────────────────┘
```

### 5.2 现有表改动（仅 1 处，最小侵入）

| 表 | 改动 | 原因 |
|---|---|---|
| `issue` | 新增 `requirement_id`（int FK→compliance_requirement，nullable） | 让「基线不合规」类问题挂到合规要求，打通「合规缺口 → 问题 → 整改 → 核验」闭环 |

> 其余现有表（contract / cmdb_ci / contract_item / work_order / change_order / approval / delivery / sys_audit_log）**一律不改**。

## 六、闭环流程与状态机

### 6.1 核验状态机

```
未覆盖 ──发起核验──▶ 进行中 ──结果=通过──▶ 已核验
                       │
                       └─结果=不通过/部分──▶ 有缺口 ──自动建 issue(requirement_id 挂接)──▶ 整改闭环
                                                                                          │
                                                         整改效果=通过（submit_round）─────┘──▶ 已闭环
```

- `有缺口 → 已闭环`：复用现有 `issue → rectification → rectification_record`，当该 requirement 关联的所有 issue 均「已关闭」时，核验自动置「已闭环」。
- `已核验` 为「本期达标」终态；`已闭环` 为「经过整改后达标」终态。

### 6.2 证据自动采集规则（收编点）

| 触发事件（现有动作） | 生成证据 | source_type |
|---|---|---|
| 工单 status 流转到「已完成」 | 自动证据 | `工单` |
| 整改轮次 effect=通过 | 自动证据 | `整改` |
| 变更单 status=已完成 | 自动证据 | `变更` |
| 交付 sign=已签署 | 自动证据 | `交付` |
| 审批 status=已通过 | 自动证据 | `审批` |
| 审计日志写入 | 自动证据（可选） | `审计` |

> 实现：在各服务层写库处调用统一的 `evidence_service.collect(...)`，与现有 `audit_service.record(...)` 同模式、同事务提交。

## 七、量化指标口径

| 指标 | 口径 | 用途 |
|---|---|---|
| **合规覆盖率** | 已关联履约证据的合规要求数 ÷ 合规要求总数 | 履职覆盖广度 |
| **闭环率** | （已核验 + 已闭环）要求数 ÷ 合规要求总数 | 风险处置完整性 |
| **留痕完整率** | 有证据的要求数 ÷ 合规要求总数 | 全程可溯程度 |
| **风险敞口** | 状态 ∈ {未覆盖, 有缺口} 且超期的要求数 | 待处置风险量 |
| **超期率** | 超期未核验数 ÷ 应核验数 | 处置时效 |

## 十、分阶段实施路径（重构渐进式，可回退）

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P1 合规底座** | 4 张新表 + 迁移 0026；`issue` 加 `requirement_id`；要求/证据/核验 CRUD；`evidence_service.collect` 接工单完成与整改通过两路自动采集 | 合规台账可手工建要求、挂证据、看证据链 |
| **P2 闭环收编** | 核验状态机 + 不通过自动建 issue；收编变更/交付/审批为证据源；`contract_insight` 增覆盖缺口预判 | 合规闭环打通，缺口自动进整改 |
| **P3 履职报告 + 指标** | `duty_report` 生成/签署；`overview` + `dashboard` 增合规指标 | 履职自证可输出，量化可控 |
| **P4 防篡改增强（可选）** | 证据哈希链 / 审计日志哈希链 | 证据不可抵赖 |

> 每阶段独立可交付、可回归；任一阶段停止都不破坏已有功能。

## 十二、待确认决策点（评审时拍板，附推荐默认值）

1. **合规要求来源范围**：P1 先做「监管要求模板库 + 人工录入」，还是同步做「合同义务自动提取」？
   → 推荐：P1 仅监管模板 + 人工录入；合同义务自动提取复用 49 步的合同抽取能力，放到 P2。
2. **证据自动采集范围**：P1 先接「工单完成 + 整改通过」两路，其余（变更/交付/审批/审计）P2 再收编？
   → 推荐：是（收敛首批改动面，降低回归风险）。
3. **履职报告聚合维度**：项目（contract）维度 / 客户维度 / 合同原件维度？
   → 推荐：项目维度为主，客户维度为辅（`project_id` 可空即客户全局）。
4. **合规要求是否引入「周期复测」**：同一要求按月/季重复核验？
   → 推荐：是，`compliance_check` 表天然支持多轮，但 P1 先做单轮，周期复测 P3 再上。
